# Thomas Hub 流体背景：实现与改进空间

核查日期：2026-10-22。当前项目：`D:\thomas-hub`。
本轮修复仅在本地，未上线。

## 先说明本次卡住的原因

这次不是首先遇到了算力瓶颈，而是页面交互逻辑主动暂停了模拟。
上一版 `main.js` 发现纵向拖动超过 8 像素就进入翻页状态，随后关闭背景动画循环。
慢速拖动持续多久，暂停就持续多久，因此看上去像“长按把背景卡住”。

本轮已把策略改为：桌面拖动和过渡时继续模拟；触屏设备在翻页手势期间优先保证页面流畅。
第二页背景完全淡出后、标签页不可见时，仍暂停无用渲染。
保留系统“减少动态效果”设置。

首屏向下、第二屏向上的提示都已恢复为两道错峰的箭头，2 秒循环、相差 1 秒，
通过位移和透明度表现方向。减少动态效果模式显示静态箭头。

## 它是怎样实现的

当前 `src/js/background.js` 保留 Pavel Dobryakov 的 MIT 许可，核心结构与
[WebGL-Fluid-Simulation 原作者源码](https://github.com/PavelDoGreat/WebGL-Fluid-Simulation/blob/master/script.js)
一致：直接使用 WebGL、GLSL 着色器和 GPU 纹理，没有使用 Three.js、视频或现成的粒子动画库。
优先申请 WebGL 2，上下文不支持时尝试 WebGL 1，并检查浮点纹理相关能力。

它模拟的是二维平面里的速度和染料流动。画面虽然看着有体积和发光感，
并不是一整池带真实水面、折射和水花的三维液体。
原仓库也明确引用了 NVIDIA 的
[GPU Gems 第 38 章](https://developer.nvidia.com/gpugems/gpugems/part-vi-beyond-triangles/chapter-38-fast-fluid-dynamics-simulation-gpu)，
其中介绍了把网格流体计算映射为 GPU 纹理运算的方法。

结合当前代码，可以把流程理解为：

```text
按住并移动指针
    ↓
在对应位置注入速度和颜色（splat）
    ↓
计算旋涡并增强卷曲细节
    ↓
计算散度 → 迭代求压力 → 减去压力梯度
    ↓
让速度搬运速度自身，让速度搬运染料；逐渐消散
    ↓
着色、明暗增强和可选泛光 → 显示到 canvas
```

速度、染料、压力等场存放在 GPU 的纹理里；着色器一次处理大量网格单元。
计算时通过两张纹理交替读写（ping-pong），避免同一次计算把输入覆盖。
拖动带来的局部速度使颜色沿流场卷动；压力校正让运动接近不可压缩流体。
最终的明暗和泛光让二维染料产生柔和、有厚度的观感。

## 当前本地版本已经采用的取舍

以下数字直接读取当前本地配置，而不是原项目默认值：

| 项目 | 桌面 | 触屏设备 |
| --- | --- | --- |
| 速度模拟基础分辨率 | 128 | 64 |
| 染料基础分辨率 | 512 | 256 |
| 压力迭代次数 | 20 | 10 |
| 画布像素倍率上限 | 1.5 | 1 |
| 明暗增强、泛光 | 开启 | 关闭 |
| 光束后处理 | 关闭 | 关闭 |

分辨率值对应纹理的短边，另一边会按宽高比扩展，并不是固定的正方形。
没有线性过滤能力的兼容分支仍会把染料分辨率设为 512，
可能反而增加低端设备的负担，应纳入后续优化。

## 性能：值得先做什么

| 优先级 | 代码中可见的机会 | 建议与收益边界 |
| --- | --- | --- |
| 高 | 画质只按指针类型粗分，不能反映真实 GPU 负载 | 先采集交互时帧时间，再在 2～3 档画质之间调整；不要每帧重建纹理 |
| 高 | `resizeFBO`、重建压力/散度等缓冲时，旧 GPU 资源未显式释放 | 尺寸变化后释放被替换的纹理和帧缓冲，减少反复旋转、缩放后的显存累积 |
| 高 | `initFramebuffers` 仍调用已关闭的光束缓冲初始化，手机上也会准备泛光缓冲 | 仅为开启的效果分配资源，减少初始化和缩放成本 |
| 中 | 没有设备负载对应的帧率预算 | 可选择 60/30 帧策略，但要同步设计时间步；当前 dt 有上限，直接跳帧会改变模拟流速 |
| 中 | 无显式 WebGL context lost/restored 恢复路径 | 丢失上下文时优雅回退，恢复后重建资源，避免长期黑屏或失效 |

不能仅凭代码给出“提升百分之多少”的承诺。本轮没有做真实手机 GPU 帧时间、
温度或功耗测量；应先确认目标设备，再对比相同拖动轨迹下的帧时间和长时间运行情况。

## 交互：流体和翻页不要争用同一个动作

本轮已经解除桌面拖动造成的主动暂停，但纵向拖动仍同时有翻页含义。
若桌面端更重视“玩流体”，可进一步让左键拖动专门搅动背景，翻页由滚轮、箭头和键盘承担；
触屏端继续保留有阻力的上下滑动。这个交互取舍尚未擅自替换，等本地体验反馈后决定。

另一个可改进点是指针输入：当前只保留最近一段移动位移，再在渲染帧里处理。
事件频率不同可能影响注入强度和轨迹细节。可按帧累计输入、适当插值并限制最大冲量，
使慢拖连续、快甩不过曝，同时避免为每个事件都增加一次完整模拟。

当前整合只处理主指针；若要恢复多指绘画，需要先明确它与手机双指缩放、单指翻页的关系。

## 美观：优先调参数和构图，而不是叠更多特效

- **配色**：当前随机全色相容易出现亮黄、亮紫等强烈色块。可以改成有限的冷色/暖色组合，
  保留少量高亮点，让页面更统一。
- **文字可读性**：可以弱化标题周围的染料注入或加很轻的局部暗化，避免高亮颜色经过文字时抢夺注意力。
- **流动质感**：联动调整 `CURL`、`SPLAT_RADIUS`、`SPLAT_FORCE` 和消散速度，
  在“细腻烟雾”和“浓厚墨水”之间选定一种方向；单独拉高某一项容易显得躁动或糊成团。
- **发光**：减少过强的泛光与大块随机初始喷溅，保留暗背景和局部亮边，通常更适合作为个人主页背景。

这些是基于当前实现的设计建议，本轮没有替换色盘或重做视觉，以免把修复和审美调整混在一起。

建议下一轮顺序：先确定桌面拖动的用途，再做资源释放与按需分配，
然后在目标手机上测量，最后比较两三个配色/流动参数方案。

## 本轮验证

- 本地构建通过，8 组导航与背景暂停策略测试通过。
- 新增回归场景：PC 慢速纵向按住拖动时背景保持 active；触屏手势暂停后能恢复。
